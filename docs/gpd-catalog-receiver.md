# GPD: приём журнала каталога на клиенте

Первый клиентский этап — приём метаданных без изменения каталога магазина.
`shop.gpd.catalog.receive` получает manifest/bootstrap, затем ленту изменений и
проверяет pending через batch. Он НЕ импортирует карточки, не меняет цены/остатки,
не деактивирует и не удаляет товары. Старый SkeeksSuppliersController не изменён.
Следующий этап — отдельный применяющий обработчик и правила владения полями.

## Состояние

- `shop_gpd_connection`: ID подключения, сайт, адрес v2, отпечаток ключа,
  фаза, курсор, граница ленты, поколение и счётчики первоначальной выгрузки.
- `shop_gpd_catalog_state`: одна строка на подключение/товар — последняя полученная
  ревизия, ревизия карточки, операция, необходимость уточнения и поколение manifest.
  JSON и ключ API здесь не хранятся. Это состояние протокола, не очередь выполнения.
- Записи страницы и курсор фиксируются одной транзакцией под блокировкой подключения.
  Сбой до commit оставляет старый курсор; повтор безопасен. Параллельный ответ со
  старым курсором отклоняется. Работа с HTTP выполняется вне транзакции.
- `revision` — порядок состояния товара, `position` — позиция события в ленте.
  Позднее событие может возвращать более новую текущую карточку. Эти числа нельзя
  смешивать; курсор принимается как непрозрачная строка от API.
- pending сохраняется явно. Отсутствие в законченной выгрузке означает необходимость
  batch-проверки, а не разрешение удалить товар. `not_available` без ревизии также
  не считается revoke. Просроченный курсор запускает новый bootstrap, сохраняя
  прежние состояния до проверки полного manifest. 401/403/503/invalid_cursor ничего
  не очищают. Смена ключа, сайта или URL блокируется как смена идентичности; для
  ротации нужен отдельный проверенный перенос подключения, автоматического reset нет.

## Native job и opt-in

Регистрация типа и очереди `gpd-receive` сама по себе ничего не запускает.
Расписания и подключения по умолчанию отсутствуют. Перед пилотом:

1. Установить код cms-shop и применить его миграцию
   `m260917_030000_gpd_catalog_receiver` штатным cms/migrate.
2. На сервере API отдельно разрешить v2 после проверки готовности журнала.
3. В конфигурации КЛИЕНТСКОГО сайта добавить компоненту gpdReceiver:

```php
'connections' => [
    'main' => [
        'enabled' => true,
        'siteId' => 1, // фактический cms_site.id, не копировать без проверки
        'url' => 'https://gpd-api.skeeks.com/v2',
        'apiComponent' => 'skeeksSuppliersApi',
    ],
],
```

Ключ берётся из указанного существующего компонента и не помещается в job payload.
ID подключения глобально уникален в установке и не переиспользуется для другого API.
В одной БД можно принимать метаданные разных подключений; это ещё не гарантирует
поддержку нескольких источников существующим импортом карточек.

4. Развернуть отдельный worker `yii cms-job/worker --queue=gpd-receive`.
5. Создать расписание с job_type `shop.gpd.catalog.receive`, payload
   `{"connection":"main"}`, правильным сайтом и интервалом 60 секунд. Сначала
   проверить ручной запуск. Нынешние четыре команды не переключаются автоматически.

Ресурс и dedup относятся к подключению; overlap=skip, до трёх попыток при сбое.
Обработчик использует ChunkedJobHandler, страницы по 50, batch по 20, перезапуск
процесса примерно через 15 секунд. Нет собственного worker, claim или retry loop.
Каждый запуск один раз проходит unresolved; если они остались, результат — с
предупреждением и следующим штатным запуском. Перед переключением на применение
надо убрать параллельных старых писателей карточек, но при проверке только приёма
они могут продолжать работать.

## Проверки и границы

`tests/gpd-catalog-receiver.php`: отдельная MariaDB 10.5, префиксы пустой и sx_,
10 000 товаров через настоящий ChunkedJobHandler, принудительные продолжения,
отмена, rollback страницы, ревизии, восстановление, изоляция подключений и прогресс.
HTTP и содержимое API в этой проверке задаёт транспортная фикстура; это не пилот
на рабочем клиенте и не проверка импорта CMS-моделей. TLS transport запрещает
redirect и не включает ключи/ответы сервера в исключения.

API ограничивает активные bootstrap-сессии: потеря ответа на создание сессии может
привести к 429 до её истечения. Не обходить лимит бесконечным bootstrap. Периодический
job повторит запрос; идемпотентное создание сессий — отдельное улучшение протокола.
Полные свойства, очистка картинок/коллекций, справочники, локальные правки,
деактивация, ACK применения, offers и переключение старых расписаний ещё впереди.
