# Системные задания магазина

shop/agents/update-subproducts и shop/notify/quantity-emails используют native
cms-job через jobType в конфигурации прежних ключей расписания. Их записи
сохраняют ID, интервал, даты и включённость; is_system=1 даёт стандартный замочек.

shop.update-subproducts работает в очереди maintenance, разделяет блокировку
shop:catalog с другими операциями каталога, обновляет SQL порциями до 1000 ID.
Между порциями проверяются отмена и heartbeat. На MariaDB отдельный запрос
ограничен 60 секундами. Планировщик только публикует задание и продолжает работу.
Общий лимит задания 2 часа, аварийные автоматические повторы выключены.

shop.quantity-emails сохраняет отключённое поведение прежней команды.
Результат содержит причину пропуска, писем задание не отправляет.

Миграция m260920_223000_system_shop_jobs переводит обе известные команды
и отмечает пять известных типов GPD как системные, сохраняя их payload и расписание.
Новые расписания GPD также создаются системными. Пользовательские задания не меняются.

Перед миграцией остановите старый процесс расписания выбранного сайта:
если запись ещё running и процесс жив, миграция откажется создавать параллельного
исполнителя. После выкладки перезапустите только воркер maintenance этого сайта
и возобновите его расписание. Общие cron, MySQL, Apache и nginx не останавливаются.

Проверки: native-maintenance-smoke.php (отдельная MariaDB), system-shop-jobs.php
(SQLite), gpd-schedule-upgrade.php и gpd-legacy-process-guard.php.
Основной источник системности — cmsAgent.commands/jobs в config/common.php.
cmsAgent/init штатно ставит is_system=1 и восстанавливает конфигурационные поля.
Пять расписаний GPD зарегистрированы в jobs; миграция нужна для уже установленных
сайтов без отдельного init, а не вместо конфигурации. is_active штатный init не меняет.
Интервалы GPD задаются конфигом. Старый параметр connection больше не нужен:
ReceiverComponent выбирает сохранённое подключение сайта и сохраняет его курсоры;
неоднозначное подключение вызывает ошибку. Настройки проекта могут явно задать
jobPayload в конфигурации соответствующего задания.

### Транзакции пересчёта складских цен

Каждая SQL-порция фиксируется до записи прогресса и продления lease задания.
Общей транзакции на все товары сайта нет: она удерживала блокировки строк
цен и cms_job_run, мешая другим заданиям и запросам посетителей.
При отмене уже выполненные порции сохраняются; повтор идемпотентного
пересчёта доводит оставшиеся цены до актуального состояния.
